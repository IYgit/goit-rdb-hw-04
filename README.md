## Схема

**Raw-рівень** (`olist_*_raw`, 6 таблиць) дзеркалить CSV як є, з типами, які виводить `pandas`.
Завантаження — через `COPY ... FROM STDIN` (`psycopg2.cursor.copy_expert`), а не `DataFrame.to_sql`:
`to_sql` шле рядки по одному й на 112 тис. позицій займає хвилини замість секунд.

**Typed-рівень** — 6 таблиць Olist плюс `olist_customer_dim`, разом **10 `PRIMARY KEY`**,
**9 `FOREIGN KEY`**, **20 `CHECK`** і `UNIQUE` на бізнес-ключі сегментів.

Ключові рішення:

* **`olist_order_reviews` не використовує `review_id` як PK.** У цій копії датасету 99 224 рядки
  містять лише 98 410 унікальних `review_id` (**814 повторів**), а 547 замовлень мають 2–3 відгуки
  (максимум — 3). Тому первинний ключ технічний — `review_row_id BIGINT GENERATED BY DEFAULT AS
  IDENTITY`, а `review_id` лишається звичайним джерельним атрибутом.
* **`NUMERIC(12,2)` для грошей**, не `FLOAT`: сума 112 650 позицій має бути точною до копійки.
* **`TIMESTAMP` без таймзони**: Olist віддає наївний бразильський час.
* **7 `CHECK` у `olist_products`** у формі `… IS NULL OR … >= 0` — розміри й ваги не можуть бути
  відʼємні, але цілком можуть бути `NULL` (610 товарів без картки).

**Службові таблиці:** `seller_alerts`, `seller_score`, `customer_segments`. Назви взяті дослівно
з умови завдання, оскільки критерії прийняття посилаються на них саме так.

### Дві речі, заради яких зроблено окремі докази

1. **`seller_score` не множить review через item-level join.** Наївний `items ⋈ reviews` дає
   **112 372** review-рядки замість **99 247** (+13.2 %) і змінює середній рейтинг **1 264**
   продавцям із 3 095. Тому дані спершу зводяться до грануляності `seller_id × order_id`,
   а відгуки окремо агрегуються до рівня `order_id`.
2. **`customer_segments` рахується за `customer_unique_id`, а не `customer_id`.** За `customer_id`
   середня кількість замовлень дорівнює рівно **1.0000** — frequency у RFM вироджується в константу,
   а 2 997 повторних покупців (рекорд — 17 замовлень) зникають. 99 441 `customer_id` відповідають
   **96 096** реальним покупцям.

Опорна дата для recency береться **з датасету** (`MAX(order_purchase_timestamp)::DATE + 1 =
2018-10-18`), а не з `CURRENT_DATE` — інакше числа мінялися б при кожному запуску.

## Як запустити

**Google Colab** (рекомендовано): відкрити notebook за badge вище → `Runtime → Run all`.
Усі залежності ставить перша клітинка, PostgreSQL 16 піднімається вбудованим `pgserver`
(без Docker), дані беруться з репозиторію або дзеркала.

**Локально:**

```bash
py -3.12 -m venv .venv && . .venv/Scripts/activate   # Linux/macOS: . .venv/bin/activate
pip install pgserver psycopg2-binary "sqlalchemy>=2.0" pandas jupysql kagglehub tzdata jupyter
jupyter lab HW4.ipynb                                 # далі Restart & Run All
```

> **Python 3.12, не 3.13.** Для `pgserver` 0.1.4 колеса зібрані під cp39–cp312; під 3.13 їх немає.

> **Windows.** Колесо `pgserver` для Windows не містить каталогу `share/postgresql/timezone`,
> тому сервер стартує з `TimeZone=GMT`, а `SET TIME ZONE 'UTC'` падає. Notebook лагодить це сам:
> функція `ensure_pg_timezone_files()` копіює `site-packages/tzdata/zoneinfo` у
> `site-packages/pgserver/pginstall/share/postgresql/timezone`. У Colab/Linux вона нічого не робить.

> **SQLAlchemy 2.1.** Починаючи з цієї версії `postgresql://` віддається драйверу `psycopg` (v3),
> тому notebook явно фіксує `postgresql+psycopg2://` — саме `psycopg2` дає `cursor.copy_expert()`
> для `COPY`.

Notebook сам визначає середовище: у Colab шляхи будуються від `/content`, локально — від поточного
каталогу. Каталог кластера PostgreSQL — `<tempdir>/hw4_pg`.
